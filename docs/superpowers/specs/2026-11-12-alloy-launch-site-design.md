# Alloy: launch site, signed releases and self-updating

Date: 2026-11-12. User request: "I want to create a gh pages to launch this editor app". Decisions quoted below are
the user's; everything else is **my call**.

## Intent

A visitor lands on the page and, ideally, leaves having downloaded Alloy (user: "Ideally they have downloaded the app
by the end"). The first thing they should take in: Alloy is "super fast and built with swift and metal" (user). Once
installed, Alloy "should update it self" (user). The user has an Apple Developer account (user).

Three parts, built in this order because each needs the one before: **(1) signed, notarised releases**, **(2) in-app
updates**, **(3) the site**.

## Part 1: signed, notarised releases

- A release script (`scripts/release-macos.sh <version>`) builds on `scripts/bundle-macos.sh`: release build, Developer
  ID Application signature with the hardened runtime and a timestamp (entitlements file in `Packaging/macOS/`, only
  what Alloy needs), notarisation with `xcrun notarytool submit --wait` using a keychain profile, stapling, then a
  DMG (drag-to-Applications layout) that is itself signed, notarised and stapled. It verifies with `spctl -a -vv` and
  `codesign --verify --deep --strict` and stops on any failure.
- Version: `CFBundleShortVersionString` = the version argument (semver, starting at 0.1.0); `CFBundleVersion` = a
  monotonically increasing build number. The git tag is `v<version>`.
- The script never handles secrets itself: it reads the signing identity name and the notarytool keychain profile name
  from environment variables. The user creates the certificate (Xcode → Settings → Accounts → Manage Certificates →
  Developer ID Application) and runs `xcrun notarytool store-credentials` themselves. **(my call: credentials stay in
  the user's keychain; nothing secret in the repo or in CI)**
- Publishing: the script creates a GitHub Release on the public repo (`gh release create`) with the DMG and release
  notes, after the public sync. Releases are cut locally on the user's Mac, not in CI. **(my call: avoids putting the
  Developer ID certificate and notary credentials into GitHub secrets)**
- Bundle identifier: **`com.unicornlabs.Alloy`** (user, 2026-11-12), replacing `dev.alloy.Alloy` in Info.plist before the
  first release; it is permanent from then on (Sparkle and macOS identify the app by it). Alloy's data directory is
  `<appSupport>/Alloy`, not derived from the bundle id, so existing data is unaffected.
- The first public release ships with the updater (Part 2) built in, so every installed copy can update itself. It does
  not wait for LSP phase 1; the Languages section lists what has shipped by then. **(my call)**
- Requirements stated on the page and in Info.plist: Apple silicon, the macOS version Alloy already requires
  (`LSMinimumSystemVersion` as today), and the Claude Code CLI installed and logged in.

## Part 2: in-app updates

- **Sparkle 2** (SwiftPM binary package, pinned exact version), bundled as `Contents/Frameworks/Sparkle.framework`
  by the bundle script and signed with the app. **(my call: the standard, audited updater; writing our own downloader
  and installer is riskier)**
- Updates are EdDSA-signed (Sparkle's `generate_keys`; the private key lives in the user's keychain, run by the user;
  the public key goes in Info.plist as `SUPublicEDKey`). Sparkle also checks the new version's code signature matches.
- Feed: `appcast.xml` served by the GitHub Pages site (`https://mburger89.github.io/Alloy/appcast.xml`), generated by
  the release script with Sparkle's `generate_appcast` from the release DMG(s), enclosure URLs pointing at the GitHub
  Release assets. Release notes are shown from the release's Markdown rendered to HTML in the appcast.
- Behaviour: check automatically once a day and at launch (Sparkle's scheduler); download in the background; install
  on quit, with a "Restart to update" action. The user can turn automatic checks off and "Check for Updates…" by hand.
  **(my call)**
- UI: Sparkle's core (`SPUUpdater`) with a **custom user driver** that shows Alloy's own MetalUI UI — a small banner or
  sidebar row "Alloy 0.2 is ready — Restart to update", release notes in a sheet, and a "Check for Updates…" menu item
  and a Settings row (automatic checks on/off, last checked). No Sparkle AppKit windows. **(my call: keeps the whole
  app MetalUI; if a needed MetalUI piece is missing it is filed as a gap, not worked around)**
- Updating never interrupts running Claude sessions: the install happens on quit (Alloy's existing shutdown already
  stops sessions first), never mid-session.
- Privacy: the update check sends only what Sparkle needs (no system profiling: `SUEnableSystemProfiling` = NO).

## Part 3: the site

Hosting stays GitHub Pages from the public repo via the existing `.github/workflows/pages.yml`. The landing page
becomes the site root (`/`); the benchmark page moves to `/benchmarks/` with a redirect from any old deep links
(`/data/*` paths keep working). `appcast.xml` is served at the root.

### Page content (top to bottom, agreed with the user on mockups)

1. **Hero** (user picked the screenshot-first direction): "Fast. Native. Yours." / "The code editor for Claude Code —
   written in Swift, drawn on the GPU with Metal." Primary **Download for Mac** button (latest release DMG), secondary
   "View on GitHub". A line under it: version · requirements · signed & notarised · free, MIT. A short looping video of
   real use under it (with a still poster; plays muted, respects `prefers-reduced-motion`).
2. **Proof strip**: three headline numbers from the latest published benchmark (e.g. benchmarks ahead of Zed,
   memory with a 2 MB file open, zero web views).
3. **Race** (user picked): "Feel the difference." An animated comparison for a chosen test, replayed from the
   published benchmark JSON. **Only tests where Alloy really wins are offered** (my call: honesty). Alloy races Zed on
   every such test; Delta appears only where the benchmark measured it (today: startup) (my call);
   footnote with machine, macOS and refresh rate, and a link to `/benchmarks/`.
4. **Shared notes** (user: emphasise it): title **"Stop paying to read the same file twice."**, subtitle **"Your
   sessions share what they learn."** (user's wording choice), the animated three-step flow (session reads a file →
   shared note → another session asks the notes, no re-read), the three benefits (less waiting, less usage, more room
   in context), and the promise that notes are tied to the exact file state and never served stale.
5. **Feature rows**, alternating image and text: many Claude sessions on one folder; who changed what (per-session
   colours and diffs, keep or revert); sessions that don't collide (overlap warnings).
6. **Themes**: Dracula default, the built-in themes (Dracula, Alloy Dark, Alloy Light, Solarized Dark and Light, …) as swatches that re-theme the hero screenshot on hover, and "make
   your own with Claude".
7. **Languages**: the 15 built-in grammars plus language servers (as shipped by LSP phase 1 by launch time).
8. **How it's built**: Alloy (Swift 6) → MetalUI (its own GPU UI framework) → Metal; no Electron, no web view.
9. **Privacy**: no telemetry, no account, runs your own Claude Code; "never changes your Claude Code settings — the
   optional theme skill is installed only when you click it" (my call: the accurate form, since the theme-skill button
   writes `~/.claude/skills/alloy-theme`); the update check is the only network call Alloy itself makes.
10. **FAQ**: free? Claude subscription needed? Intel Macs? How do updates work? How is it so fast?
11. **Closing download**: "Try it in a minute." + Download, release notes link, source link.

### Site constraints

- Static HTML and CSS, generated like the benchmark page (a Swift generator in `Bench` or a sibling target, with a
  "committed site is current" test). JavaScript only where the race and theme swatches need it, inline, no frameworks.
- No external resources: no CDN fonts, no analytics, no trackers, no cookies (system font stack). **(my call:
  matches the benchmark page and the privacy section's promise)**
- Every number on the page comes from published benchmark JSON at build time; no hand-typed figures.
- The Download button links to `https://github.com/mburger89/Alloy/releases/latest/download/Alloy.dmg` (a stable
  asset name), so the page needs no rebuild per release.
- Screenshots and the video are captured by the controller session from the real app (Dracula theme), on a scratch
  project with no personal data, using a few short real Claude turns; they pass the public repo's privacy gate and stay
  under its 5 MB per-file limit. **(my call)**
- Claims: speed and memory figures only from published benchmark JSON. Feature copy describes what a feature does and
  how; no unmeasured quantities (e.g. no "saves N% usage"). A feature row appears only for features that have passed
  their hands-on check in the app by launch. **(my call)**
- Responsive down to phone width; dark by default with a light variant; accessible (alt text, captions, contrast,
  keyboard focus, reduced motion).
- Lighthouse-style budget: the page is light — target under 1.5 MB total including the video poster (the video loads
  lazily), first contentful paint fast on a cold load.

## Goals summary

A signed, notarised, stapled DMG on GitHub Releases; Alloy updates itself through a signed appcast with Alloy's own
UI; a landing page at the site root that tells the speed + Swift/Metal story, features shared notes prominently, and
gets the visitor to download.

## Non-goals

Homebrew cask (later), Intel or older-macOS builds, a Windows/Linux download, a blog, a newsletter or email capture,
accounts, analytics, a custom domain, App Store distribution, delta updates.

## Anti-goals

- Any claim on the page that the published benchmark doesn't support.
- An update that can install something not signed by the user's Developer ID and EdDSA key.
- An update that interrupts running Claude sessions or loses unsaved work.
- Secrets (certificates, passwords, private keys) in the repo, in CI or in logs.
- Breaking the existing benchmark page or its data URLs.

## Steps the user does by hand (security-sensitive)

1. Install a Developer ID Application certificate (Xcode → Settings → Accounts → Manage Certificates → + → Developer
   ID Application).
2. `xcrun notarytool store-credentials alloy-notary --apple-id … --team-id …` (app-specific password).
3. Run Sparkle's `generate_keys` once (stores the EdDSA private key in the login keychain; prints the public key).
4. Approve each release run (the script asks before tagging, uploading and publishing).
